# Omnia CI/CD Pipeline

Automated cleanup, install, deployment and validation of Omnia on one or more OIMs, driven from
GitLab CI/CD. Each cluster is an independent child pipeline: if one fails, the others continue.

This folder holds the pipeline sources. `setup_gitlab_project.py` uploads them to a GitLab
project, together with the cluster inputs, and sets the CI/CD variables.

## What it does

For every cluster, in this order:

1. **Initialization** (one stage): checks the CI/CD variables and the OIM host key, clones Omnia on
   the OIM and takes the pipeline helpers (`pipeline_ci.py`, `library/`) from that clone, checks
   the input folders and SSH, records the commit, copies `omnia.env` and, before any cleanup,
   checks that the Slurm and Kubernetes NFS shares can be mounted.
2. **Cleanup**: one stage per domain runs the cleanup playbook (`./omnia.sh --run <domain> --tags
   <cleanup tag>`, with the flags of the cluster's `test_config.yml`). Every cleanup runs, even
   after one failed. Right after each one a `test_cleanup_<domain>` stage checks its result
   (`fvt_<domain> cleanup verify`, in the Omnia venv). The orchestrator one also empties the Slurm
   and Kubernetes NFS shares (its `nfs_shares` suite, selected by `cleanup_slurm` and
   `cleanup_k8s`); then the `cleanup_omnia` stage runs `omnia.sh --cleanup --all` and `test_cleanup_omnia` checks it. If any cleanup or
   cleanup test failed, nothing is installed and the pipeline ends red. If initialization fails, every other stage is skipped and only the summary runs.
3. **Install** (`setup_main`, one stage): `omnia.sh -s` creates the Omnia venv and runs every
   `domain-init`, then the inputs of every domain (`clusters/<cluster>/inputs/src/<domain>/`) and the
   catalog are copied to `<data>/<domain>/input/<project>/` on the OIM. `fvt_main verify` tests the
   install in the next stage.
4. **Domains**: repo_manager, image_build_manager, discovery (optional), orchestrator and
   telemetry. A domain stage fetches its credentials from OpenBao and runs every playbook tag, one by one in
   one stage, with `./omnia.sh --run <domain> --tags <tag>`; the next stage verifies it (`TEST_MODE=true`). A failed tag stops the
   pipeline, a failed verify does not stop the next domain.
5. **Summary**: a table of every job and one email with the verdict, the links and the test
   reports.

```
initialization > (cleanup_<domain> > test_cleanup_<domain>) per domain > cleanup_omnia > test_cleanup_omnia > setup_main
   > test_main_installation
   > <domain> > test_<domain> ... > summary
```

The modes choose the part that runs: `default` is everything, `deploy` skips the cleanup and the
install and only copies the inputs (the Omnia venv must exist), `cleanup` stops after the cleanup. See
[docs/PIPELINE_MODES.md](docs/PIPELINE_MODES.md).

Besides the cluster pipeline there are two more, selected by a project variable:
**utils** (`UTILS_ENABLE=true`: log collection, install_os, OIM log backup) and **build stream**
(`BUILD_STREAM_ENABLE=true`: `prepare_base`, then build_stream). All three are generated by
`pipeline_render.py` and run `pipeline_ci.py`, so they share the failure rules, the skip words and
the one test report; see their guides.

**Failure rules.** Every cleanup and every cleanup test runs; if any failed, `cleanup_omnia` and the
install do not run and the pipeline goes to `summary`. A failed domain deploy stops the pipeline at
once; a failed test does not stop the next domain. `summary` always runs, sends the report, and fails
the pipeline when any job failed. To run again, start a new pipeline: each pipeline has its own id,
and with it its own report.

**One report.** Every test run of a pipeline writes into one report,
`/automation/<pipeline id>_omnia_pipeline_report.html` (and `.json`) on the OIM, one suite per run:
`telemetry_cleanup`, `utils_cleanup`, `telemetry`, ... `initialization` sets `run_id`, `report_name`
and `report_path` in every module's `test_config.yml`; the values you set there are replaced.

## Folder contents

```
.gitlab-ci.yml                 Parent pipeline: reads pipeline_config.yml, triggers every cluster. GENERATED
.gitlab-ci-cluster.yml         Cluster pipeline. GENERATED by pipeline_render.py, do not edit
.gitlab-ci-build-stream.yml    Build stream pipeline. GENERATED
.gitlab-ci-utils.yml           Utils pipeline. GENERATED
pipeline_config.yml            The one file you fill in (clusters, OpenBao, mode, email)
pipeline_triggers.py           Reads pipeline_config.yml and writes the trigger jobs (parent pipeline)
setup_gitlab_project.py        Creates or updates the GitLab project, files and variables
pipeline_render.py             Generates the four pipeline files (stages, rules, order)
pipeline_ci.py                 The logic of every job (taken from the Omnia clone, see below)
ut/                            Unit tests of the helpers (python3 -m pytest test/pipeline/ut)
library/                       email_func (summary email, runs on the runner) and its vars
                               (not uploaded to GitLab: the jobs use the copy in the Omnia clone)
docs/                          The guides listed above
```

After `setup_gitlab_project.py --create`, the GitLab project holds:

```
.gitlab-ci*.yml, pipeline_triggers.py, pipeline_config.yml   (no other helper code: it comes from the clone)
clusters/<cluster>/inputs/
  src/
    main/omnia.env             Omnia environment of the OIM
    main/catalog_rhel.json     Optional catalog
    <domain>/                  The input files of repo_manager, image_build_manager, discovery,
                               orchestrator, telemetry (build_stream and utils for their pipelines)
  test/<domain>/               Optional test_config.yml and test_run_config.yml
```

A project made before this layout keeps `inputs/<domain>/`, `inputs/omnia.env` and
`catalogs/catalog_rhel.json` (`inputs/test/<domain>/` is the same); the cluster pipeline reads either
one (`inputs/src/` wins when it exists). The build stream and utils pipelines read the
`inputs/src` and `inputs/test` layout only.

## Prerequisites

| Requirement | Details |
|---|---|
| GitLab | 15.7 or later, CI/CD enabled, a runner with `python3` and `sshpass` |
| Omnia branch | `OMNIA_REPO` and `OMNIA_BRANCH` must point at a branch that has `test/pipeline/pipeline_ci.py` |
| OIM | RHEL or Rocky with `git` and `python3`, SSH on port 22, a root user. `nfs-utils` if the NFS shares are emptied |
| OpenBao | Unsealed, reachable from the runner (port 8200), JWT login for GitLab |
| Your machine | Python 3 with `pyyaml` and `requests` (for `setup_gitlab_project.py`), and `ssh-keyscan` |

## Quick start

1. Set up OpenBao and store the domain credentials: [docs/OPENBAO_SETUP.md](docs/OPENBAO_SETUP.md).
2. Fill in `pipeline_config.yml`: the OIM address and user, the Omnia repository and branch, the
   OpenBao URL, the mode and the domains.
3. Create the project, set the variables and store the OIM host key:

   ```bash
   pip install pyyaml requests
   python3 setup_gitlab_project.py --create \
       --gitlab-url https://gitlab.example.com \
       --token glpat-xxxx \
       --project-name omnia-pipeline \
       --config pipeline_config.yml \
       --scan-host-keys
   ```

4. Add the OIM password as the masked variable `<CLUSTER>_TARGET_PASS`
   (for example `CLUSTER1_TARGET_PASS`) in the project's CI/CD settings. It is never stored in
   `pipeline_config.yml`.
5. Edit the inputs in the project under `clusters/<cluster>/inputs/src/` (and the test settings under `clusters/<cluster>/inputs/test/`).
6. First run with `DRY_RUN=true` (`dry_run: "true"` in the config): every job prints what it
   would do on the OIM and changes nothing. Then run it for real: **CI/CD > Pipelines > Run
   pipeline**.

## Configuration in short

| Setting | Default | Meaning |
|---|---|---|
| `pipeline_mode` | `default` | `default`, `deploy` or `cleanup` |
| `domains` | `default` | `default` (all) or a regex such as `repo_manager\|orchestrator` |
| `test_mode` | `true` | Run the `verify` stages |
| `enable_setup` | `false` | Run the install (`setup_main`) in `deploy` mode too |
| `enable_discovery` | `false` | Run the discovery stages |
| `dry_run` | `false` | Print what would run on the OIM, change nothing |
| `verbose` | `false` | pytest `-v` and ansible `-vvv` for the FVT runs of the cluster pipeline |
| `skip_stages` | `""` | Words to skip, comma or space separated, each matched exactly: a domain (`telemetry`) skips all its stages; a stage name (`test_cleanup_telemetry`, `cleanup_omnia`, `setup_main`) skips that stage; the groups `cleanup`, `test_cleanup`, `deploy` and `test` skip every stage of that kind; `nfs_check` and `inputs` skip that step inside `initialization` and `setup_main`. See [docs/CLUSTER_PIPELINE.md](docs/CLUSTER_PIPELINE.md) |
| `deploy_tags.<domain>` | per domain | Comma list of FVT tags run in exec mode (variable `<DOMAIN>_TAGS`) |
| `test_commands.<domain>` | `./run_validation.sh fvt_<domain> verify` | The verify command (variable `TEST_<DOMAIN>_CMD`) |

All settings and variables: [docs/CONFIGURATION.md](docs/CONFIGURATION.md).

## Security

- **Host key:** the OIM host key must be known. `--scan-host-keys` stores it as the File variable
  `<CLUSTER>_SSH_KNOWN_HOSTS`. `PIPELINE_SSH_SKIP_HOST_KEY=true` accepts the risk of an unchecked
  key and prints a warning.
- **Password:** the OIM password reaches `ssh` only through the `SSHPASS` environment variable. It
  is not on a command line, in a file or in an artifact, and it is replaced by `********` in the
  job output.
- **OpenBao:** a JWT login, secrets are written to the OIM with mode 600 and vault-encrypted;
  only field names reach the logs. TLS is verified with `BAO_CA_CERT`. The default stays
  unverified, with a warning, as it always was.
- **NFS:** the shares are emptied by the orchestrator cleanup (`nfs_shares` suite of
  `test/orchestrator`, `cleanup_slurm` / `cleanup_k8s` choose the shares), and nothing is deleted
  unless the share was mounted read-only first. System directories and the Omnia checkout are never emptied. See
  [docs/CLUSTER_PIPELINE.md](docs/CLUSTER_PIPELINE.md#nfs-share-cleanup).
- **Concurrency:** one pipeline per cluster at a time (`resource_group`); runner failures are
  retried once; artifacts expire after a week.

## Changing the pipeline

The stages, their order and their rules are tables in `pipeline_render.py`. After a change:

```bash
python3 pipeline_render.py --write     # regenerate .gitlab-ci-cluster.yml
python3 pipeline_render.py --check     # exit 1 when the committed file is out of date
```

Details and how to add a domain: [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).
