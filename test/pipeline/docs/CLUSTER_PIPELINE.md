# Cluster Pipeline

How the cluster pipeline (`.gitlab-ci-cluster.yml`) works. It is generated by
`pipeline_render.py`; every job calls `ci_tools/pipeline_ci.py`, which runs the work on the OIM over SSH. Nothing but the YAML is uploaded
to the GitLab project: the `initialization` job clones Omnia on the OIM and copies
`test/pipeline/pipeline_ci.py` and `test/pipeline/library/` out of that clone into `ci_tools/` (an
artifact, code only) for the later jobs. `OMNIA_BRANCH` must therefore be a branch that has them.
For the settings see [CONFIGURATION.md](CONFIGURATION.md), for the modes
[PIPELINE_MODES.md](PIPELINE_MODES.md).

---

## The flow

```
 initialization        ONE stage: clone Omnia on the OIM and take the helpers from it; checks of
                       the variables, the host key, the inputs and SSH; the commit and omnia.env;
                       (DOMAINS=default) every NFS share mounts read-only
 cleanup_<domain>      omnia.sh --run <domain> --tags <cleanup tag> with the flags of the cluster's
                       test_config.yml (repo_manager: cleanup_pulp, the others: cleanup)
 test_cleanup_<domain> fvt_<domain> cleanup verify in the Omnia venv, right after its cleanup; the
                       orchestrator one empties the Slurm and K8s NFS shares
                       (one cleanup, one test, per domain, in the order build_stream, utils,
                       telemetry, orchestrator, discovery, image_build_manager, repo_manager;
                       none is tolerated)
 cleanup_omnia         ONE stage: omnia.sh --cleanup --all (fvt_main cleanup exec, test/main venv)
 test_cleanup_omnia    ONE stage: fvt_main cleanup verify, what the Omnia reset must have left
 setup_main            ONE stage: omnia.sh -s, then the inputs of every domain and the catalog
 test_main_installation  fvt_main verify
 <domain>              omnia.sh --run, tag by tag: repo_manager, image_build_manager, discovery,
                       orchestrator, telemetry (one stage each)
 pxeboot               orchestrator --tags pxeboot: runs only after the orchestrator stage passed;
                       test_orchestrator runs only after pxeboot passed
 test_<domain>         verify of that domain (the next stage)
 summary               job table, the test reports, one email
```

| Stage | `default` | `deploy` | `cleanup` | Condition |
|---|---|---|---|---|
| initialization | yes | yes | yes | the NFS check only with `DOMAINS=default` in `default` and `cleanup` |
| cleanup_\<domain\> | yes | | yes | the domain is selected |
| test_cleanup_\<domain\> | yes | | yes | the domain is selected |
| cleanup_omnia | yes | | yes | `DOMAINS=default` |
| test_cleanup_omnia | yes | | yes | `DOMAINS=default` |
| setup_main | yes | inputs only | with `ENABLE_SETUP=true` (install only) | install in `default` or with `ENABLE_SETUP=true`; inputs in `default` and `deploy` |
| test_main_installation | yes | yes | | `TEST_MODE=true` |
| \<domain\> | yes | yes | | the domain is selected (discovery: `ENABLE_DISCOVERY=true`) |
| test_\<domain\> | yes | yes | | `TEST_MODE=true` |
| summary | yes | yes | yes | always runs |

Any stage can be skipped with `SKIP_STAGES`, a comma or space separated list of words, each matched
exactly (`telemetry_x` does not match `telemetry`):

| Word | Skips |
|---|---|
| a domain: `repo_manager`, `image_build_manager`, `discovery`, `orchestrator`, `telemetry`, `utils`, `build_stream` | every stage of that domain: its cleanup, cleanup test, deploy and test |
| a stage name: `cleanup_<domain>`, `test_cleanup_<domain>`, `test_<domain>`, `cleanup_omnia`, `test_cleanup_omnia`, `setup_main`, `test_main_installation`, `summary` | that stage only |
| `cleanup` / `test_cleanup` / `deploy` / `test` | all the `cleanup_<domain>` / all the `test_cleanup_<domain>` / all the domain deploy stages / `test_main_installation` and all the `test_<domain>` |
| `nfs_check` | the NFS check inside `initialization` |
| `inputs` | the input copy inside `setup_main` |

Skipping a cleanup but not its test (or the other way round) is allowed; a test stage whose cleanup
did not pass fails with that reason.

**What stops what:**
- A failed `initialization` skips every other stage: only `summary` runs.
- A failed domain deploy (`<domain>`) stops the pipeline at once: its test and the later domains are
  skipped, and `summary` runs.
- A failed test (`test_main_installation`, `test_<domain>`) does not stop anything: the next domains
  still deploy and test.
- A failed cleanup or cleanup test does not stop the other cleanups and cleanup tests, but then
  `cleanup_omnia`, the install (`setup_main`) and every later stage are skipped and `summary` runs
  (below). Nothing is tolerated by default; `pipeline.tolerate_failures` in `pipeline_config.yml`
  names jobs whose failure does not block the install or fail the pipeline (they still show as
  failed in the report and the mail).
- `summary` always runs, sends the report, and fails the pipeline when any job failed (a failed
  test too), so the pipeline is red when all stages ran but a test failed.

## A failed cleanup stops the install

The rule: every cleanup and every cleanup test runs, then `cleanup_omnia` runs, and if any of them
failed nothing is installed or deployed.

- The cleanup jobs, the cleanup tests and `cleanup_omnia` are `allow_failure` and each needs
  `initialization` plus the earlier ones (`needs`, optional), so each runs in order even after
  another one failed, and a failed `initialization` skips all of them.
- The first job that would change anything after the cleanups, `setup_main` (and every domain
  exec after it), first calls `require_cleanups_ok`: it fails, with a red pipeline, when a cleanup or
  a cleanup test failed (`utils` and `discovery` included). That skips every later stage.
- `cleanup_omnia` (the destructive `omnia.sh --cleanup --all`) is run only when every cleanup and
  every cleanup test passed.
- `summary` always runs and fails the pipeline when any job failed.
- The cleanup jobs also check the `pipeline_job_status/initialization.ok` marker, which the
  initialization job leaves only when every step passed (the clone, the checks, the NFS check).
- A cleanup stage runs only the playbook; no test runs in it. Its test stage runs afterwards. A
  passed cleanup leaves the marker `pipeline_job_status/cleanup_<domain>.ok`; without it the test
  stage fails with "cleanup_<domain> did not pass, so its result is not verified".

A cleanup on an OIM without an Omnia venv (the very first run) finds nothing to clean and passes.

## `pipeline_ci.py`

The commands of the jobs, in the order of the pipeline. The clone itself is made by a small inline
bootstrap in the `initialization` job. It checks the host key policy like the helper does and
checks out `OMNIA_REPO` at `OMNIA_BRANCH` on the OIM the way the SVT does (`update`, `recreate` or
`keep`, below), because the helper does not
exist before the clone. All of them need the cluster variables
`<CLUSTER>_TARGET_IP`, `_TARGET_USER`, `_TARGET_PASS`.

| Command | What it does |
|---|---|
| `initialize` | The whole initialization stage: `init`, `checkout` and, in `default` and `cleanup` mode with `DOMAINS=default`, `nfs-check`. Leaves the `initialization` marker only when all of them passed |
| `init` | Checks `CLUSTER`, the cluster variables, `OMNIA_REPO` and `OMNIA_BRANCH`, `OMNIA_INSTALL_PATH`, the host key policy, `clusters/<cluster>/inputs/src/main/omnia.env` and the SSH connection (retried) |
| `checkout` | Records the commit of the clone (`actual_commit_sha.txt`) and copies `omnia.env` into it |
| `nfs-check` | Every Slurm and K8s share of the OIM's `storage_config.yml` mounts read-only (nothing is deleted) |
| `cleanup <domain>` | Checks the marker, then `./omnia.sh --run <domain> --tags <tag>` in the Omnia venv with `-e` flags read from `clusters/<cluster>/inputs/test/<domain>/test_config.yml` (orchestrator: `cleanup_credentials`, `cleanup_slurm`, `cleanup_k8s`; build_stream: `postgres_backup`, `cleanup_credentials`; telemetry: `delete_sinks_volume`, `cleanup_credentials`, `cleanup_logs`; repo_manager and image_build_manager: `cleanup_credentials=false` only). No test runs |
| `cleanup-verify <domain>` | Checks the marker of the cleanup, copies the cluster's test config, sets `run_id` to the pipeline id, then `fvt_<domain> cleanup verify` in the Omnia venv (utils: `--marker cleanup`). The orchestrator one empties the NFS shares (see below). Copies the reports it wrote before the Omnia cleanup removes them |
| `cleanup-omnia-verify` | Checks the marker of `cleanup_omnia`, then `fvt_main cleanup verify` from the `test/main` venv |
| `cleanup-omnia` | Checks the marker, then runs `omnia.sh --cleanup --all --skip-approval`. When any cleanup or cleanup test failed or left no pass marker (`cleanup_<domain>.ok`, `test_cleanup_<domain>.ok`; skipped and tolerated jobs are not required) (the NFS shares may not be empty) it is not run and the Omnia venv stays |
| `setup-main` | `install` (in `default` mode or with `ENABLE_SETUP=true`), then `inputs` (in `default` and `deploy` mode) |
| `install` | `omnia.sh -s`, then checks that the venv activates |
| `inputs` | Copies the inputs (below); refuses an input folder that holds a symbolic link |
| `credentials <domain>` | Fetches the domain credentials from OpenBao and encrypts them on the OIM |
| `deploy <domain>` | `credentials`, then every playbook tag with `./omnia.sh --run <domain> --tags <tag>` |
| `pxeboot` | `./omnia.sh --run orchestrator --tags pxeboot`; its own stage between `orchestrator` and `test_orchestrator` (skip words `pxeboot`, `orchestrator`, `deploy`) |
| `stage <domain> <tag>` | `fvt_<domain> <tag> exec` |
| `verify <domain\|main>` | The test config and credentials, then the verify command |
| `prepare-base` | Build stream pipeline: the credentials of `repo_manager`, `image_build_manager` and `orchestrator`, then `./omnia.sh --prepare-base`; blocked when a cleanup failed |
| `setup-utils` | Utils pipeline: `install` (`omnia.sh -s`), then the inputs of the `utils` domain |
| `summary` | Prints the job table, fetches the test reports, sends the email |

Domain and tag names are checked against fixed lists and patterns before they reach a command.
`DRY_RUN=true` makes every command print what it would run on the OIM and change nothing.

## The Omnia checkout on the OIM

The `initialization` bootstrap checks out `OMNIA_REPO` at `OMNIA_BRANCH` into `OMNIA_INSTALL_PATH` on
the OIM, with the same modes as the SVT. The mode is the project variable
`<CLUSTER>_CHECKOUT_MODE` (or `CHECKOUT_MODE`), default `update`:

| Mode | What it does |
|---|---|
| `update` | Fetches and checks out the branch in the existing clone, or clones it when there is none |
| `recreate` | Stops what still runs in the folder, deletes it and clones again. Refused for system folders |
| `keep` | Uses the existing clone as it is (it must be a git checkout) |

The OIM needs `git` and `python3`. Without them the stage stops with `install git and python3 on
the OIM (it needs an enabled package repository)`. The helpers (`pipeline_ci.py`, `library/`) are
then copied from that checkout into `ci_tools/` for the later jobs.

## Inputs

The inputs are copied by the `setup_main` stage after `omnia.sh -s` (in `default` and `deploy` mode),
which has created the domain folders and their default inputs. For every deploy domain (repo_manager, image_build_manager, discovery, orchestrator,
telemetry) that has a folder `clusters/<cluster>/inputs/src/<domain>/` in the
project, its content is copied to `<OMNIA_DATA_PATH>/<domain>/input/<OMNIA_PROJECT_NAME>/` on the
OIM (both resolved from the Omnia venv). The catalog `clusters/<cluster>/inputs/src/main/catalog_rhel.json`
is copied to `<data>/catalog/` when present. The stage fails if no domain folder exists or a copy
fails. The project layout is `clusters/<cluster>/inputs/src/<domain>/`, `inputs/src/main/` (omnia.env and
catalog) and `inputs/test/<domain>/`; a project with the older `inputs/<domain>/` layout is still read
(`inputs/src/` wins).
`pxe_mapping_file.csv` is given mode 640, which the orchestrator validation requires, and
`secret.yaml` mode 600.

**Paths that follow the OIM.** Omnia needs absolute paths that exist for the files an input names
(for example `csi_powerscale_driver_secret_file_path`, `csi_powerscale_driver_values_file_path`,
`pxe_mapping_file_path`, `additional_cloud_init_config_file`, `repo_manager_output_path`,
`csm_observability_values_file_path`). Write them with `$OMNIA_DATA_PATH` and
`$OMNIA_PROJECT_NAME` (or `${OMNIA_DATA_PATH}` / `${OMNIA_PROJECT_NAME}`), for example
`"${OMNIA_DATA_PATH}/orchestrator/input/${OMNIA_PROJECT_NAME}/secret.yaml"`. While it copies a
domain folder the stage replaces these placeholders in the `.yml` / `.yaml` files with the values of
the OIM (`OMNIA_DATA_PATH` and `OMNIA_PROJECT_NAME` of its `omnia.env`), so Omnia sees plain
absolute paths and a changed data path or project name needs no edit of the inputs. The files
`secret.yaml` and `values.yaml` are copied as they are and never rewritten, and only these two
names are replaced. The copy is made in a private temporary folder (mode 700) that is removed
afterwards. `secret.yaml` and `values.yaml` of the project folder are pushed on every run, so a
changed secret or values file reaches the OIM with the next pipeline.

## Domain stages

`deploy <domain>` fetches the credentials, then runs the playbook tags of the domain one by one,
in ONE stage, each as `./omnia.sh --run <domain> --tags <tag>` in the Omnia venv, and stops at the
first failure. The verify stage that follows still runs `./run_validation.sh fvt_<domain> verify`:

**With tags or without.** `deploy_tags.<domain>` in the config (variable `<DOMAIN>_TAGS`, a comma
list such as `prepare,execute`) runs exactly those tags, one `./omnia.sh --run <domain> --tags <tag>` each. With no list the
domain's default tags run in order:

| Domain | Default tags |
|---|---|
| `repo_manager` | `precheck`, `prepare`, `execute`, `status` |
| `image_build_manager` | `validate`, `prepare`, `build` |
| `discovery` | `precheck`, `validate`, `execute` |
| `orchestrator` | `precheck`, `prepare`, `provision`; then the stage `pxeboot` (tag `pxeboot`) |
| `telemetry` | `precheck`, `validate`, `deploy` |

**Verbose.** `VERBOSE=true` adds `-v --ansible-verbosity 3` to every FVT call (pytest `-v` and
`ansible-playbook -vvv`). `--ansible-verbosity <0-4>` is a runner option of every domain and sets
the environment variable `OMNIA_ANSIBLE_VERBOSITY`; without it the ansible verbosity stays at the
default of the test configuration (1).

Before every FVT call the test requirements of the domain are installed and the `omnia_auto`
wheel of the checkout (`test/plugins/dist`) is force-installed, so the branch under test is the
code that runs.

**Credentials.** The login is the GitLab JWT (`VAULT_ID_TOKEN`, audience `BAO_SERVER_URL`, role
`BAO_AUTH_ROLE`); the secret is read from `<BAO_DATA_PATH>/<domain>`. The values are written to
`<data>/<domain>/input/<project>/` with mode 600 and encrypted with `ansible-vault` (a key file
is generated if missing). File names: `repo_manager_config_credentials.yml`,
`image_build_credentials.yml`, `discovery_credentials.yml`, `orchestrator_credentials.yml`,
`telemetry_credentials.yml`. Missing discovery credentials only warn; for the other domains the
stage fails. Only the number of fields is printed.

**Test stages.** `verify <domain>` copies `test_config.yml` and `test_run_config.yml` from
`clusters/<cluster>/inputs/test/<domain>/` (defaults of the checkout when absent), the test
credentials (the File variable `<CLUSTER>_TEST_CREDS`, and for orchestrator and telemetry the
OpenBao secret `test_<domain>`, which wins), encrypts them, then runs the command. The command is
`TEST_<DOMAIN>_CMD`, default `./run_validation.sh fvt_<domain> verify`; it must start with
`./run_validation.sh` and use plain characters only.

## NFS check in the initialization stage

When the orchestrator is selected the initialization stage checks the NFS shares before anything
is cleaned. It reads the NFS entries (`fs_type: nfs`) of the project's
`clusters/<cluster>/inputs/src/orchestrator/storage_config.yml`, so it works on the first run, before
Omnia is installed. From the OIM, for every share: the NFS server answers on port 2049, then the
export is mounted read-only on a temporary folder and unmounted. Every share is checked and one
line is printed per share (`OK` or `FAIL` with the reason: no answer, mount refused, `nfs-utils`
missing). A failed share fails the initialization, so every other stage is skipped and the mail
shows the reason. `SKIP_STAGES=nfs_check` skips it. The check needs `nfs-utils` on the OIM.

---

## NFS share cleanup

The orchestrator cleanup playbook only unmounts the shares and removes their fstab entries; it
never deletes NFS data. The shares are emptied by the `nfs_shares` suite of the orchestrator
cleanup FVT (`test/orchestrator/fvt/cleanup/nfs_shares`), so the stage `test_cleanup_orchestrator`
does it and the same check can be run by hand on the OIM:

```bash
cd test/orchestrator
./run_validation.sh fvt_orchestrator cleanup verify
```

For both values of `cleanup_slurm` / `cleanup_k8s` of `test/orchestrator/test_config.yml` the suite
first checks that the share is unmounted and has no fstab entry. `true` then empties the share
(`nfs_slurm`, `nfs_k8s`); `false` keeps the data and mounts nothing.

It empties the mounts `nfs_slurm` and `nfs_k8s` of the `storage_config.yml` in the orchestrator
input folder of the OIM (`<OMNIA_DATA_PATH>/orchestrator/input/<OMNIA_PROJECT_NAME>/`). On an OIM
without that file, or without NFS mounts in it, there is nothing to empty and the test is skipped.

1. The check in `initialization` (read-only): every share is mounted read-only and unmounted. A
   share that cannot be reached fails the stage, so no cleanup runs.
2. The `nfs_shares` suite in `test_cleanup_orchestrator`, after the orchestrator cleanup
   playbook: the share is checked again first (unmounted, no fstab entry), mounted read-only as a
   preflight, then mounted on a new private folder that is never added to fstab, emptied
   completely (the export itself stays) and unmounted. A fresh read-only mount then counts the
   entries; a connected client can recreate files, so the empty-and-check cycle is repeated, up to
   three attempts. If it fails, `test_cleanup_orchestrator` fails and `cleanup_omnia` does not run
   `omnia.sh --cleanup --all`.

The Omnia cleanup itself goes through `run_validation`: `test/main` (`cleanup_all: true`, set by
the pipeline) runs from its own `test/main/.venv` (`./setup_env.sh --venv`, then
`./run_validation.sh fvt_main cleanup test`), because the cleanup removes the Omnia venv and
`fvt_main cleanup` refuses to run from it.

Safety rules (`test/orchestrator/library/functions/nfs_func.py`): the emptying tests are marked
`destructive`; no shell is used; the source must be an IPv4
address or host name and an export of plain characters without `.` or `..`; system directories
(`/`, `/etc`, `/opt`, `/var`, and so on) are never emptied, nor an export on the OIM that holds
the Omnia checkout, the data path or `/etc/omnia`; the mount point is checked in
`/proc/self/mountinfo` to be an NFS mount of exactly that source; deletion works on open
directory descriptors, never follows a symbolic link and never crosses into another mount; the
share is always unmounted.

Requirements: a local run as root on the OIM, `nfs-utils`, and an export with `no_root_squash`
for the OIM.

## SSH and secrets

- The OIM host key must be known: the File variable `<CLUSTER>_SSH_KNOWN_HOSTS` (stored by
  `setup_gitlab_project.py --scan-host-keys`) or `PIPELINE_SSH_KNOWN_HOSTS`. With neither, the job
  fails. `PIPELINE_SSH_SKIP_HOST_KEY=true` skips the check and prints a warning.
- The password goes to `ssh` only through `SSHPASS`, and `********` replaces it in any output.
  The pipeline writes no `target.env`.
- OpenBao TLS: `BAO_CA_CERT` verifies it; `BAO_TLS_SKIP_VERIFY=false` verifies with the system
  certificates; the default is unverified, with a warning.

## Summary, HTML report and email

The `summary` job always runs. It reads `pipeline_job_status/*.json` (name, status and job link
of every job, written by the `after_script` of each job), prints the table and exits 1 when a
job failed. Then it copies the HTML and JSON test reports written during this pipeline from
`TEST_REPORTS_PATH` (default `/automation`) on the OIM to `pipeline_reports/`, and sends
one email when `EMAIL_RECIPIENTS`, `EMAIL_SENDER` and `SMTP_SERVER` are set
([EMAIL_NOTIFICATIONS.md](EMAIL_NOTIFICATIONS.md)). A mail that cannot be sent is reported in a
banner in the log but does not change the result of the pipeline.

**The HTML report** `pipeline_report/pipeline_<id>_report.html` (a job artifact, and attached to the
mail) is one file without external assets: the pipeline information, cards, and one collapsible
block per stage with its status, duration, failure reason and its **whole log in a scrollable
pane**. It has a day and a night theme (the system setting, with a button), a filter, a search in
the stage names and logs, expand and collapse all, line wrapping and a copy button; very long logs
keep their head and their tail. The logs come from the GitLab API with the masked, protected CI/CD
variable `PIPELINE_API_TOKEN` (a project access token with the `read_api` scope, role Reporter; the
job token cannot read logs). Without it, each stage uses the output its own job kept in
`pipeline_job_logs/` (the output of the helper, without GitLab's own `$ command` lines).

**One test report for the whole pipeline.** Right after the clone, the `initialization` stage sets
`run_id` (the pipeline id), `report_name` (`omnia_fvt_pipeline_report`) and `report_path`
(`TEST_REPORTS_PATH`, default `/automation`, created with mode 750) in the `test_config.yml` of
every module of the clone; every later FVT run sets the same three values again after the cluster's
test config is copied. All runs therefore write into one report,
`<report_path>/<pipeline id>_omnia_fvt_pipeline_report.html` and `.json`, and its suite breakdown has one
suite per run: `<domain>_<tag>` for a tag (`telemetry_cleanup`, `utils_cleanup`,
`build_stream_cleanup`, ...) and `<domain>` for a run without a tag (`telemetry`). The suite that
ran last is at the top; the layout of the report is unchanged. The folder is outside `/opt/omnia`,
so the Omnia cleanup does not remove it. `initialization` deletes reports of earlier pipelines
older than `REPORTS_KEEP_DAYS` (default 30) from it. A retried job replaces the earlier result of
the same test in the report instead of adding it again. Only the summary copies it, once. The mail gets exactly two
attachments: that test report (HTML) and the HTML report of the stages; the JSON and the full
stage report are job artifacts.

## Runs

- One pipeline per cluster at a time: the trigger jobs use `resource_group: pipeline-<cluster>`.
- A job is retried once after a runner system failure, an API failure or a scheduler failure. A
  failing script and a timed out job are not retried.
- Artifacts expire after one week. Each job times out after 3 hours.

## What changed from the previous pipeline

| Before | Now |
|---|---|
| Inline shell in the YAML, repeated per domain | `pipeline_ci.py`; the YAML is generated |
| `StrictHostKeyChecking=no`, `known_hosts` removed | Host key required |
| `TARGET_PASS` in the `target.env` artifact | `SSHPASS` only, no file |
| (cluster pipeline) `initialization`, `setup_environment` and `nfs_check` were three stages, `inputs` and `cleanup_nfs` stages of their own | One `initialization` stage (clone, checks, NFS check); `setup_main` installs after the cleanup |
| Cleanup by playbook tags | The cleanup playbook with `omnia.sh --run`, then `fvt_<domain> cleanup verify` in its own stage |
| Cleanup failure stopped the pipeline immediately | All cleanups run, then it stops without installing |
| NFS shares kept their data | Slurm and K8s shares emptied by `test_cleanup_orchestrator` (`nfs_shares` suite) |
| Inputs copied inside each domain job | Copied once, in the `setup_main` stage |
| `<DOMAIN>_TAGS` were ansible tags | Playbook tags run one by one with `omnia.sh --run` |
| A separate test venv per domain | The test requirements go into the Omnia venv |
| No concurrency limit | One pipeline per cluster |
| Plain email | Email in the SVT layout |

The utils and build stream pipelines are unchanged.
